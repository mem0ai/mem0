# Bug bash 2026-08-03 — plan for what code alone can't close

This doc covers the parts of MEM-5919 that were CONFIRMED but not fully closeable from this
repo, plus Finding 5 (informational). Code-fixed items are in the branch commit, not repeated
here in detail; see the PR description / commit message for the fix list.

## Finding 1 — Codex: hooks off by default, no shell env docs, no Codex Cloud mention

**Status:** partially fixed, partially blocked.

Fixed in this branch: `docs/integrations/codex.mdx` now states plainly that hooks are opt-in
(installer script + `codex_hooks` feature flag), matching `scripts/install_codex_hooks.py`'s own
docstring and `integrations/mem0-plugin/README.md`. Added a "Codex Cloud" section documenting the
Environment Variable vs. Secret persistence split (secrets are wiped before the agent phase;
`MEM0_API_KEY` must be an Environment Variable for MCP calls to keep working). Also fixed a
second, previously-undocumented drift: `README.md` said the installer merges "three entries"
(SessionStart, UserPromptSubmit, Stop) while the actual template
(`hooks/codex-hooks.json`) has six event groups (adds PreToolUse ×3, PostToolUse ×2, PreCompact);
`scripts/install_codex_hooks.py`'s own print statement had the same undercount. Both now match the
template.

**What blocks the rest:** the underlying platform limitation — Codex has no plugin-host mechanism
to auto-wire hooks from an installed plugin — is real and cannot be fixed from this repo; it's an
OpenAI Codex product constraint, not a Mem0 bug. Whether the doc fix actually resolves the bug-bash
reporter's confusion needs a live Codex session (app + CLI + Cloud) to confirm the installer runs
cleanly end-to-end and hooks actually fire after enabling the feature flag. I do not have a Codex
environment in this sandbox to run that check.

## Finding 2 — Cursor: `/add-plugin mem0` fails ("MCP server does not exist: mem0"), loops on auth

**Status:** one cosmetic path fix applied; root cause not confirmed without live Cursor.

Fixed in this branch:
- `integrations/mem0-plugin/.cursor-plugin/plugin.json` had `"mcpServers": ".cursor-mcp.json"`
  (bare filename, no `./` prefix) while the equivalent Codex file uses
  `"mcpServers": "./.codex-mcp.json"`. Normalized to `"./.cursor-mcp.json"` for consistency.

**Considered and rejected:** normalizing `.cursor-plugin/marketplace.json` (repo root) to the
`interface`/object-`source`+`policy` schema used by `.codex-plugin/marketplace.json` and
`.agents/plugins/marketplace.json`. Cursor's published reference
(https://cursor.com/docs/reference/plugins) documents the Claude-style schema the file already
uses: a required `name`, an `owner` block, optional `metadata`, and plugin entries with a **string**
`source`. Swapping in the Codex schema would move the file *away* from the documented shape, so it
was reverted. The one deviation from the doc's example worth testing is the leading `./` in
`"source": "./integrations/mem0-plugin"` — the reference example uses a bare relative path
(`"source": "plugin-one"`) and offers a `pluginRoot` prefix field. Left alone because
`.claude-plugin/marketplace.json` uses the same `./` form and works.

**What blocks the rest:** the applied fix is not confirmed to be *the* root cause of "MCP server
does not exist: mem0" — that message could equally stem from Cursor requiring an explicit
marketplace registration step (`codex plugin marketplace add` has a Cursor analog we haven't found
in this repo — `cursor.mdx` never mentions a plugin marketplace or `/add-plugin` at all, only
MCP-only install). This repo has no Cursor client to test against. Recommend: get one bug-bash
reporter to retest `/add-plugin mem0`; if it still fails, capture the exact Cursor plugin-log
output (Cursor's plugin host logs, not just the chat error) to identify whether it's a manifest
issue, a missing registration step, or something else. If a registration step turns out to be
required, `docs/integrations/cursor.mdx` needs a new "Plugin Marketplace" section analogous to
`codex.mdx`'s Option A — not added here because the exact CLI/UI syntax is unverified.

**Separate drift found while checking:** all three `plugin.json` files declare `"version":
"0.2.13"` while `.claude-plugin/marketplace.json` and `.cursor-plugin/marketplace.json` declare
`"0.2.14"`. Not corrected here — picking the right number is a release call, not a bug-bash one.

## Finding 4 — Antigravity: plugin hooks all dead

**Status:** fixed (silent-failure bug); the "missing Setup/PreCompact" sub-claim is REFUTED.

Fixed in this branch: `integrations/mem0-plugin/hooks.json` (root, Antigravity's hook file) piped
three of its hook commands through `2>/dev/null || true`, which swallows stderr *and* forces exit
0 — so a broken hook (missing `python3`, a script path that doesn't resolve, etc.) fails completely
silently, with no way for a user to tell hooks are dead versus just not doing anything. Verified
red (a real failing script under `2>/dev/null || true` produces empty stderr and exit 0) and green
(same script under `|| true` alone surfaces the stderr message, exit still forced to 0 so it stays
non-blocking). Dropped `2>/dev/null` from all three affected commands, kept `|| true`.

Re: Antigravity's `hooks.json` lacking `Setup` and `PreCompact` entries that
`hooks/hooks.json` (Claude Code's file) has — this is **not a bug**.
`docs/integrations/antigravity.mdx` documents exactly five hook events for Antigravity
(SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop) with no mention of Setup or
PreCompact, so the hooks.json file matches its own documented scope. Whether Antigravity's host
actually fires a `PreCompact`-equivalent event at all is unverifiable from this repo (no live
Antigravity access), so even if it were desirable to add, we can't confirm `${extensionPath}` +
`PreCompact` would do anything. Leaving as documented scope; revisit only if Antigravity gains
(or is confirmed to already have) a compaction lifecycle event.
